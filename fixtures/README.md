# fixtures/

A small synthetic lakehouse every skill's evals run against. No client data, ever -- everything here is
generated by `generate_fixtures.py` (built in Phase 1 alongside `data-discovery`, the first skill whose
evals needed it), not hand-written or exported from anywhere real.

Build it with:
```
python fixtures/generate_fixtures.py
```
This writes `bronze.db`, `silver.db`, and `gold.db` under `fixtures/lakehouse/` (gitignored --
regenerate anytime; fixed seed, so the output is identical every time).

## Why local simulation instead of a real Databricks workspace

This toolkit targets Databricks/Unity Catalog in production, but evals need to run offline and
reproducibly (in CI, with no workspace, credentials, or network dependency). `generate_fixtures.py`
builds the fixture lakehouse in **SQLite** (Python's standard library, so running evals never requires
installing anything -- see `DECISIONS.md`: the original plan was DuckDB, but SQLite is stdlib-only and
was substituted without loss of the underlying design). Every skill's deterministic scripts are written
against a thin adapter layer (`scripts/lakehouse_adapter.py`, shared across skills) so the same code
path runs against the local SQLite fixture in eval/CI (`SQLiteFixtureAdapter`) and against a real
Databricks SQL warehouse in production (`DatabricksAdapter`), both exposing the same
profile/sample/constraint/orphan-check interface. The three-level Unity Catalog `catalog.schema.table`
hierarchy is simulated by `ATTACH`ing one SQLite file per schema (`bronze.db`, `silver.db`, `gold.db`)
to a single connection; the "catalog" (`acme_retail_dev` in every example/eval) is just a config label.

## What's in the fixture lakehouse

- `bronze.raw_orders` -- an uncurated raw-ingestion table: messy PascalCase source-system naming,
  string-typed everything, a `_rescued_data` column, duplicate re-ingested rows, no comments. Exists so
  `data-modeling`'s silver-layer verification has something to correctly *refuse* to build gold from.
- `silver.customers` -- curated customer dimension source, with a **duplicated natural key**:
  `customer_number` `'CUST-1042'` appears on three different `customer_id` rows (42, 121, 122) --
  the surrogate key stays unique throughout, so this flaw only surfaces if you check the business key
  specifically, which is the point.
- `silver.customer_region_history` -- effective-dated region history for two customers, the
  **slowly-changing attribute** scenario `data-modeling` should recognize as SCD type 2 material.
- `silver.orders` -- curated order-line fact source (grain: one row per `order_id, line_number`), with:
  a **broken FK** (one row's `customer_id` is `99999`, which doesn't exist in `silver.customers`); a
  **nullable column that shouldn't be** (`ship_region` is null on ~2.6% of rows despite no `NOT NULL`
  constraint and no legitimate reason to be null); and a **type mismatch** (`total_amt` is declared
  `TEXT`, though every value parses cleanly as a decimal -- the column comment even says so). This
  mismatch is meant to be caught by `data-discovery`'s `looks_numeric_but_declared_text` profiling
  signal and flagged in a generated contract's `assumptions[]` -- it does NOT surface as a
  `data-validation` discrepancy, because normalization correctly coerces numeric-looking text before
  comparing (working as designed; see `references/normalization-and-type-coercion.md`). An earlier
  version of this file claimed otherwise -- corrected after the Phase 3 judgment-inclusive
  integration sign-off run caught the discrepancy between this doc and the actual (correct) behavior.
- `gold.legacy_fct_orders` -- a pre-existing (not toolkit-generated) production gold table standing in
  as a validation **target**, built via an inner join that silently drops the orphaned-customer order --
  exactly the discrepancy `data-validation` (Phase 2) is meant to find against `silver.orders` as source.

Table and column comments (used by `data-modeling`'s curated-silver check and by discovery's grounding)
are stored in companion `_table_comments`/`_column_comments` tables within each schema file, since
SQLite has no native `COMMENT ON` -- see `generate_fixtures.py` for the exact values.

## Integration check: proving the five skills' artifacts actually chain together

Each skill's own `evals/run_assertions.py` tests that skill's scripts in isolation. Neither that,
nor the subagent scenario evals, prove that skill A's real output is actually a valid input to
skill B -- an artifact can be individually schema-valid and still not fit the next stage's real
expectations. `integration_check.py` is a fully deterministic (no LLM, CI-runnable) run of the
whole chain against the real fixture lakehouse:

```
python fixtures/generate_fixtures.py
python fixtures/integration_check.py
```

It resolves `contracts/examples/model-spec.example.json` (data-modeling's output) into a real,
schema-valid `data-contract.json` (data-discovery, resolution mode) by grounding every mapping
against profiled `silver.orders`/`silver.customers` columns, feeds that contract into
`data-pipeline` to generate real code and prove local idempotency, then attaches `data-quality`
(contract-derived checks against `silver.orders`) and `data-validation`
(`silver.orders` vs `gold.legacy_fct_orders`) at their gates -- five schema-valid artifacts from
one continuous run, written to `fixtures/integration/` (generated, gitignored, same treatment as
`fixtures/lakehouse/*.db`). See the script's own docstring for exactly what this does and doesn't
prove -- it caught six real inconsistencies in this toolkit's own shipped examples during
construction (see `CHANGELOG.md` and `DECISIONS.md`), which is exactly the kind of bug this check
exists to catch and the scenario evals alone would not have.

## Layout

```
fixtures/
├── generate_fixtures.py     builds the fixture lakehouse deterministically (fixed seed, stdlib sqlite3)
├── integration_check.py      proves the five skills' artifacts chain together end to end (see above)
├── README.md                 this file
├── local-overrides/          gitignored -- a project may drop extra synthetic fixtures here
├── integration/               generated, gitignored -- integration_check.py's output artifacts
└── lakehouse/                generated, gitignored, not committed
    ├── bronze.db
    ├── silver.db
    └── gold.db
```
