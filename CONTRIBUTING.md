# Contributing

## The rule that overrides every other rule

**No client data, client schema names, client sample values, client business terminology, or anything
else identifying a specific engagement ever enters this repo.** Not in a fixture, not in an example
artifact, not in a test prompt, not in a commit message, not in an issue or PR description. Before you
open a PR, re-read your diff specifically looking for this. If you're generalizing something you built
on an engagement, rewrite every identifying detail (company names, column names, business terms, actual
figures) into something synthetic before it goes anywhere near this repo.

`fixtures/` is the one place table-shaped data lives in this repo, and it is 100% synthetically
generated by `fixtures/generate_fixtures.py` -- never a sanitized export of anything real. If you're
adding a new deliberate flaw to the fixture lakehouse for a skill's eval, add it to the generator script,
not as a hand-edited data file.

## Making a change

1. **Schema changes** (`contracts/*.schema.json`) are the highest-blast-radius change in this repo --
   every skill reads or writes against them. Before changing one:
   - Decide if it's additive (new optional field: patch/minor) or breaking (removed/renamed/retyped
     required field, changed enum values a consumer switches on: major). See `README.md` "Versioning".
   - Update the corresponding example in `contracts/examples/` and re-run
     `python scripts/validate_artifact.py contracts/examples/<name>.example.json` -- CI does this for
     every example on every PR, but check locally first.
   - Update every skill's SKILL.md / scripts that read or write that schema. A schema change that isn't
     reflected in the skills that use it is an incomplete PR, not two PRs.
   - If it's a major bump, add a `CHANGELOG.md` entry explicit about what breaks and what a project
     pinned to the old major needs to do.

2. **Skill changes** (`skills/<name>/`) follow the `skill-creator` skill's loop: draft or edit
   `SKILL.md` / `references/` / `scripts/`, run the skill's `evals/evals.json` test prompts against the
   shared `fixtures/`, and don't merge a skill change without a passing eval run recorded (attach the
   eval run output or a link to it in the PR). If your change affects triggering (the `description`
   field), run the description optimization loop described in the skill-creator skill before merging --
   an under- or over-triggering skill degrades every other skill it might collide with.

3. **Cross-cutting rule changes** (`references/toolkit-conventions.md`) apply to all six skills by
   reference. If you change a rule here, check whether any skill's SKILL.md restates (rather than
   references) the old version of that rule and needs a matching edit.

4. **Fixture changes** (`fixtures/`) should come with a note on which skill(s)' evals depend on the flaw
   or scenario you're adding/changing, since fixtures are shared infrastructure -- a change here can
   silently break another skill's assertions.

## Before opening a PR

- [ ] No client-identifying content anywhere in the diff (see the rule above).
- [ ] `python scripts/validate_artifact.py` passes on every touched/added example artifact.
- [ ] Affected skill(s)' evals pass against `fixtures/` (attach output).
- [ ] `SKILL.md` files you touched are still under ~500 lines; if not, move detail into `references/`.
- [ ] `CHANGELOG.md` updated, including a note on schema major-version impact if applicable.

## Review

At least one other person reviews schema changes and cross-cutting convention changes before merge, given
how many skills depend on both. Skill-local changes (a `references/` doc, a fixture-eval tweak) can move
faster.
